# Mobile debugging and edge cases

All facts below are pinned to Dioxus `fda3dc9c2b10ddf4417edcbb98caa9613ac92d26` in `/root/repo/dioxus`.

## Triage order

1. Record platform, device or simulator, target triple, profile, `dx` command, and first failing phase.
2. Separate Rust compile, native link, package generation, Gradle or Xcode tool, install, process startup, WebView load, IPC, and app logic failures.
3. Inspect earliest native log. Later WebView blank screen or poisoned lock can be secondary.
4. Inspect generated package at `target/dx/...`, not only source tree.
5. Reproduce once without hot patch assumptions. Then test rebuild or host recreation separately.

## Android startup

Use `adb logcat` around process launch. Search first native exception, `UnsatisfiedLinkError`, panic, and WebView error.

- `UnsatisfiedLinkError`: compare generated `dev.dioxus.main.MainActivity`, Wry Kotlin `Rust` object, JNI symbols generated by Tao and Wry bindings, and loaded `lib<lib_name>.so`. Evidence: `packages/cli/assets/android/MainActivity.kt.hbs` and `packages/desktop/src/mobile.rs:1-55`.
- `Failed to find main symbol`: `start_app` could not resolve `main` or `_main` through `dlsym`. Evidence: `packages/desktop/src/mobile.rs:69-78`.
- `ndk_context` panic followed by `PoisonError`: verify pinned `start_app` runs once-guarded initialization before Wry setup. Evidence and rationale: `packages/desktop/src/mobile.rs:20-50`.
- Native panic at JNI boundary aborts process by design after logging. Evidence: `packages/desktop/src/mobile.rs:59-67`.
- Debug env missing: `.env` is loaded from Android session cache only in debug. Malformed lines without `=` are skipped. Evidence: `packages/desktop/src/mobile.rs:80-95`.

## Recreation and concurrency

Rotation, theme changes, and foreground or background transitions can recreate Android Activity and reenter setup. NDK context remains process-global due `Once`; do not assume Activity object identity remains stable.

Pinned desktop renderer uses Android synchronization lock around event handling, VDOM polling, rendering, and hot patching because Wry paths are not fully thread-safe. Evidence: `packages/desktop/src/webview.rs:109-115` and `packages/desktop/src/app.rs:335-349,447-465`. Native callbacks should schedule work through supported event-loop paths rather than mutate WebView from arbitrary threads.

DOM edits use a local WebSocket rather than long-polling because of Android Wry bugs. `packages/desktop/src/edits.rs:1-19` documents random-key protection and automatic port/key replacement when iOS sleep kills the socket. After resume, distinguish expected reconnect from dead event-loop wakeup; `packages/desktop/src/waker.rs:17-20` records missing upstream iOS support.

## Blank or broken WebView

- Confirm app reaches `dioxus://index.html/` and custom protocol serves index and assets: `packages/desktop/src/webview.rs:395-430`.
- Internal Dioxus URL may navigate only once. Later navigation to another Dioxus page is rejected after first load: lines 406-415.
- HTTP, HTTPS, and mail links open externally and WebView navigation is canceled: lines 417-424.
- Android custom protocol opts into HTTPS scheme for secure-context APIs: lines 432-438.
- Mobile suppresses desktop menu and desktop default window size: lines 263-272 and 497-505.
- Debug mode enables Wry devtools unless context menu is disabled. Release behavior differs: lines 477-495.

## Hot reload and hot patch

`packages/desktop/src/app.rs:316-413` queues devserver messages until initial DOM rebuild, applies hot patch only after WebViews exist, reloads stylesheets when assets change, and distinguishes full reload from hot patch. A successful Rust patch does not prove native Kotlin, Swift, manifest, plist, Gradle, entitlement, or linker changes were rebuilt. Restart full package for native-boundary changes.

## Permissions

Debug three separate states:

1. Declaration exists in generated AndroidManifest or Info.plist.
2. Runtime request executes on supported platform API.
3. User or OS grants access and result returns to Rust.

If state 1 fails, inspect `ManifestMapper` and generated files. If state 2 fails, inspect browser secure context or native plugin. If state 3 fails, inspect platform callback, denial, restricted state, and lifecycle recreation. Do not solve runtime denial by adding duplicate manifest entries.

## Native plugins

Android:

- Confirm metadata extraction found source directory or AAR.
- Confirm plugin appears under generated `plugins/` or `app/libs/`.
- Confirm `settings.gradle` and `app/build.gradle.kts` include it.
- Confirm ABI and JNI contract independently of Gradle success.

Apple:

- Confirm Swift package path and `Package.swift` product.
- Confirm `xcrun swift build` target and SDK.
- Confirm framework exists under `.app/Frameworks` and Swift runtime libraries were embedded.
- Confirm code signature after framework insertion.
- Treat class lookup and call ABI as plugin-specific until source proves names.

## iOS investigation boundary

Use Simulator logs, `xcrun simctl`, `codesign --verify --deep --strict`, bundle inspection, and linker symbol inspection. Pinned source proves package, simulator, signing, Swift framework, UIKit handle, and Wry adaptation paths. It does not prove app host bootstrap. Report that gap when startup fails before Dioxus launch. Do not invent AppDelegate, SceneDelegate, `@main`, C symbol, or Swift bridge.

## WGPU confusion

A blank HTML WebView is not automatically a WGPU issue. `dioxus-desktop` depends on Wry and Tao, not WGPU. Investigate WGPU only when app imports WGPU, uses native renderer package, or embeds a GPU child surface. Mixing native GPU surface with WebView adds platform handle, surface lifetime, resize, and thread constraints outside ordinary mobile renderer contract.

## Known edge cases

- Current-thread Tokio runtime is rejected by desktop launch: `packages/desktop/src/launch.rs:170-190`.
- Raw `launch_virtual_dom` creates no implicit window. Root must render `Window`: `packages/desktop/src/launch.rs:51-60,149-170`.
- Android release assembly path checks legacy `bundle.android`; verify task choice when using newer `[android.signing]` config.
- iOS tooling preflight is currently a no-op, so missing Xcode tools can surface late.
- IPA accepts device AArch64 only and requires verified signature.
- iOS host bootstrap remains unknown in local source.

Official docs help with expected setup. **Docs mismatch:** when docs imply a supported lifecycle callback, permission helper, plugin ABI, or iOS bootstrap not present in pinned code, record mismatch and follow source.
