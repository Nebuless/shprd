Compound Engineering · Ideation

PWA first-class installability & mobile host-connect for SHPRD

Date 2026-09-21 Topic feat-pwa-install-parity Focus first-class PWA (installability, offline shell, performance, install UX) + mobile host-entry connect bug Mode: repo-grounded

Codebase Context

  • Stack: Bun bridge (server/src) serves the built React/Vite client and embeds every asset (PUBLIC_FILES base64 map) into a single binary; Rust/Dioxus Android shell (crates/shprd-shell) injects a MOBILE_BOOTSTRAP connect form into the built index.html; desktop shell = iframe + postMessage bridge.
  • Zero PWA surface today: no manifest, no service worker, no beforeinstallprompt, no theme-color anywhere (grep-verified); index.html carries only icon + apple-touch-icon to one 158 KB 512px PNG; FEATURES.md:309-310 nonetheless claims an installable PWA.
  • The mobile bug, structurally: the bootstrap's only "connect" is window.location.assign(host); a saved bad host auto-navigates on every launch before the form can render; the same host predicate is hand-copied four times across Rust/JS surfaces.
  • Existing leverage: /api/health probe + update poll, immutable-hashed Vite builds, lazyWithReload crash guards, refreshOnReturn online/visibility handlers, clipboard + standalone-display primitives, a 200 KiB initial-JS gzip budget the server never actually serves.
  • Reference app: OpenChamber (clone analyzed as ground truth): server-generated no-store manifest + shortcuts, minimal iOS-safe SW, probe-before-connect with error taxonomy, QR /connect?t= pairing.

Topic Axes

  1. Installability surface — manifest, icons, meta tags, install prompts, iOS A2HS affordances.
  2. Offline & lifecycle shell — SW scope, caching strategy per asset class, update/reload UX, bridge-unreachable behavior.
  3. Load performance — bundle weight, code splitting, compression, cache headers, font/asset strategy.
  4. Host-entry & first-connect UX — enter/validate/test/remember/switch host URLs on Android WebView and browser; error surfaces and recovery.
  5. Device pairing & continuity — desktop-to-mobile handoff of the host URL (QR, copy-link, deep links), app identity, session resume after install.

External grounding (PWA 2026 practices, Tailscale/Termux host-entry survey) cached in the run's web-research cache; OpenChamber claims verified against its source.

1. Connect contract — one host grammar, a reachability preflight, and a first-party probe taxonomy

Host-entry & first-connect UX Confidence 86% Complexity M C1 + C2 + C13 (combination X1)

Description: Fix the mobile host-connect bug as one contract instead of three patches. (a) One host grammar: a build-generated validator with golden test vectors replaces the four hand-copied predicates (Rust HostUrl::parse, the MOBILE_BOOTSTRAP normalize string, remoteHost.ts configuredHost, shell-controls.js); input auto-corrects by stripping paths ("Connecting to https://host.example — path removed") while queries stay hard-rejected to preserve the validator's deliberate secret-refusal stance. (b) Reachability preflight: the Android bootstrap runs a bounded no-cors fetch (reachable / unreachable / timeout) before window.location.assign, and gates the saved-host auto-start behind it with a visible edit-host escape — killing the boot-loop where a typo'd saved host re-navigates into a WebView error page on every launch. (c) First-party probe taxonomy: post-navigation (where cookies work), promote /api/health's existing {ok, version, socket} shape into a versioned contract (reachable | wrong-service | needs-auth | ok) consumed by the connection banner, the update poll, and diagnostics.

Basis: direct: window.location.assign(host) + savedHost→start(savedHost) auto-start (crates/shprd-shell/src/main.rs:53-60); the same predicate hand-copied in lib.rs:19-38, main.rs:37-47, remoteHost.ts:9-28, shell-controls.js:17-25 (verifier: all four confirmed); /api/health returns {ok, version, socket} (server/src/index.ts:1223-1228). external: OpenChamber probe-before-connect with status taxonomy, connect blocked on wrong-service/unreachable (packages/ui/src/lib/desktopHosts.ts).

Rationale: The verifier confirmed the silent-assign mechanism and the duplication; it also showed the preflight must be reachability-only (<code>/api/health</code> is auth-gated; no-cors responses are opaque) — hence the deliberate split between the bootstrap's opaque probe and the first-party app's classified taxonomy.

Downsides: Validator generation adds a build step; preflight adds worst-case ~1s on the happy path; auto-strip must not extend to query strings (privacy stance in the lib.rs:14 comment).

2. Serve what you verify — immutable caching, compression, and the 902 KB font

Load performance Confidence 82% Complexity M C6 + C7 (combination X2)

Description: The build measures a 200 KiB initial-JS gzip budget and a 12 MiB total budget, but the runtime delivers bytes neither compressed nor cache-described: responseHeaders() returns content-type only, with cache-control exclusively on index.html. Close the loop: hashed assets get cache-control: public, max-age=31536000, immutable + ETag; pick baked .br siblings (embedded-binary size delta made explicit in the budget script) or runtime compression — decided deliberately because assets are base64-embedded in the single-file binary. Subset/slice herdr-nerd-symbols.woff2 (902,836 bytes) along its already-declared unicode-range so the first terminal render stops paying the whole font; fold font bytes into the budget gate.

Basis: direct: static-files.ts:59-75 (content-type-only headers; index.html no-cache exception with the updater comment); check-web-assets.mjs budgets (12 MiB / 650 KiB / 200 KiB gzip); web/src/assets/herdr-nerd-symbols.woff2 = 902,836 bytes with unicode-range already declared (styles.css:285-290).

Rationale: Every cold start over Tailscale (or a DERP relay) re-downloads megabytes; the SW precache idea inherits these bytes, so serving compressed + immutable must land before any offline shell locks the cost in. The font is the largest controllable asset and its unicode-range groundwork already exists.

Downsides: Baked precompressed siblings enlarge the embedded binary (a tension the plan must price); font subsetting adds a build tool and touches terminal glyph coverage; immutable headers are only correct while the updater's atomic index.html swap remains the invalidation mechanism.

3. SW update pipeline — precache from the build manifest, staged swap, one update UX

Offline & lifecycle shell Confidence 80% Complexity M C4 + C5 (combination X3)

Description: Generate a service-worker precache manifest from the Vite build manifest / public-files gen at build time (check-web-assets.mjs already walks exactly these files). Hashed assets cache-first; index.html network-first, honoring the existing no-cache, must-revalidate entry-document contract. The SW doubles as the update bus: it stages the next version's assets in the background, the UI offers one "Restart to apply" (skipWaiting + controllerchange at a navigation boundary, never mid-terminal-session), and the scattered hard-reload call sites (store.ts:642-644/688, lazyWithReload.ts:9-29, ConfigMenu.tsx:534, TerminalView.tsx:2277) converge on one lifecycle owner — lazyWithReload's crash-reload becomes a never-hit safety net. The cached shell is also what renders when the bridge is unreachable, instead of a blank WebView.

Basis: direct: vite.config.ts:23-27 (manifest: true, outDir ../server/public); check-web-assets.mjs walks .vite/manifest.json (lines 14-22); lazyWithReload.ts:1-8 stale-tab 404 crash comment; static-files.ts:63-70 entry-document contract. external: PWA 2026 caching matrix (cache-first hashed, network-first HTML); OpenChamber's deliberately minimal classic-IIFE sw.ts as iOS-safe prior art.

Rationale: The repo already hand-built an update-detection subsystem (health poll + reload guards + lazy-chunk crash guards) that a SW replaces structurally — and the precache list is already computed by the build.

Downsides: SW code + registration + update interplay is the largest new surface; iOS Safari SW quirks push toward a minimal classic-IIFE SW; double-life risk if the health-poll reload machine is not retired in the same change.

4. Install identity owned by the bridge — generated manifest, icon set, honest head

Installability surface Confidence 84% Complexity M C9 + C10

Description: Ship the missing install surface: a /manifest.webmanifest (name, short_name, start_url, id, scope, display: standalone, theme_color/background_color from the palette, icons 192/512 + maskable + apple-180) plus the head tags SHPRD lacks (theme-color, apple-mobile-web-app-*), closing the gap where FEATURES.md:309-310 claims installability that does not exist. Decide static-vs-generated deliberately: a static manifest fits the existing PUBLIC_FILES embedding pattern; a server-generated no-store manifest (OpenChamber parity) buys per-host naming and dynamic shortcuts to recent connections. Derive the full icon set from the single 512px PNG at build time via gen-public.ts.

Basis: direct: web/index.html:9-10 only icon + apple-touch-icon (single 158,445-byte 512px PNG, no 192/maskable variant); zero manifest/theme-color/apple-mobile-web-app matches repo-wide; FEATURES.md:309-310 claims installable PWA. external: OpenChamber server-generated no-store manifest with runtime overrides + recent-session shortcuts, plus its data-URL fallback.

Rationale: Installability is greenfield and the docs already promise it; the manifest is also the substrate the pairing and install-CTA ideas hang on, so its ownership decision shapes two other ideas.

Downsides: Generated manifests add a route + cache-policy decisions; shortcuts need a data source; maskable icons need padding-safe artwork, not a raw upscale of the existing PNG.

5. Earned install CTA — prompt at proof, with an iOS coach card

Installability surface Confidence 78% Complexity L C11

Description: Capture beforeinstallprompt at load, suppress the browser default, and release the install CTA only after the first successful bridge connect — the moment the workspace has proven itself — honoring persisted dismissal and never showing in standalone (isStandaloneDisplay already exists in downloadFile.ts). iOS, which never fires the event, gets a static A2HS coach card (Share → Add to Home Screen) in the same slot.

Basis: direct: zero beforeinstallprompt handling repo-wide; isStandaloneDisplay + share-sheet logic (downloadFile.ts:45,84-91). external: OpenChamber usePwaInstallPrompt (deferred prompt + persisted dismissal keys).

Rationale: Answers "when do we ask?" with a product answer instead of a browser default; prevents prompt fatigue before it trains users to dismiss.

Downsides: Timing policy is a product call with churn cost if wrong; the iOS coach card is manual-flow education that can feel patronizing if shown too early.

6. Pairing QR — the host handoff that is also the first connect test

Device pairing & continuity Confidence 74% Complexity M C12 (+C15, C17) (combination X4)

Description: Desktop ConfigMenu (and/or a bridge-served /connect page) renders a QR + copy-link of the validated origin; the Android bootstrap grows a scan/paste affordance (BarcodeDetector where available, clipboard fallback per the existing writeText precedent). v1 pairs the bare origin — the validator guarantees origins carry no credentials or query, so the QR leaks no secrets; a later step can add a one-time token redeemed by a new endpoint that mints the shprd_auth cookie (OpenChamber's /connect?t= generalized), which also makes the installed PWA same-origin and dissolves the packaged-page cookie constraint. The handoff IS the first-connect test: the scanned URL flows through the validator + preflight before persisting.

Basis: direct: validator rejects credentials/query (lib.rs:29-30, remoteHost.ts:17-18) and the secret-never-echoed comment (lib.rs:14); clipboard.writeText precedent (AgentHistoryCard.tsx:68); /api/login takes {password} only (auth.ts:29) so token redemption is net-new. external: OpenChamber /connect?t= pairing links + QRCode.toDataURL, multi-host list, redactSensitiveUrl.

Rationale: Typing a Tailscale URL on a phone keyboard into a form that silently fails is the #1 onboarding pain; scanning a QR of the origin the desktop is already on removes the failure mode instead of improving its error message.

Downsides: Token redemption needs a new auth path (no /api/login shape exists); the validator must accept-then-strip the pair parameter (coordinated with the connect-contract idea); camera-permission UX on Android.

7. Three-worlds connectivity — device-offline vs bridge-down vs wrong-host

Offline & lifecycle shell Confidence 76% Complexity M C3 (revised)

Description: One connectivity-state module consuming navigator.onLine reads (none exist today), an offline event listener (missing; only refreshOnReturn online/visibility handlers exist at store.ts:2143-2161), and the /api/health probe, driving three honest UI states: device offline (pause retries, cached shell, drafts retained), bridge unreachable/restarting (bounded backoff + last-connected), wrong/changed host (surface the host with the change-host affordance instead of navigating into the void). Distinct copy per state, per DESIGN.md's text-not-color-only rule.

Basis: direct: reconnectDelayMs = 1500 blind WS retry (api.ts:342); refreshOnReturn online/visibilitychange handlers exist but no state machine (store.ts:2143-2161); FEATURES.md:308-310 no-offline stance. reasoned: a UI that only exists server-fetched cannot distinguish failure causes by construction; the SW-cached shell (update-pipeline idea) is what makes the offline state renderable at all.

Rationale: The reported Android bug is indistinguishable from a server restart in the current UI; the taxonomy is shared infrastructure for the bootstrap, the connection banner, and diagnostics.

Downsides: State-machine edges (auth expiry mid-session, version skew during restart) need care; depends on the SW shell for the offline render; must consolidate with — not parallel — the existing reconnect logic.

8. Standalone host switcher — restore the lost UI outside the Dioxus iframe

Host-entry & first-connect UX Confidence 80% Complexity M C8

Description: installShellBridge only wires postMessage when parent !== window, and ConfigMenu's Shell/Host URL section renders only when shellHostUrl() is truthy — in a browser tab or installed PWA the test/switch/confirm UI is dead code, and window.__SHPRD_HOST_URL__ is read by remoteHost.ts but injected by nothing. Publish the active origin into the page (bridge-injected global or bootstrap snippet) and render the existing switch/confirm/bridge.check UI in standalone so "fix my host" is an in-app action — the recovery path that pairs with the connect-contract preflight.

Basis: direct: shellBridge.ts:122-127 + ConfigMenu.tsx:564-626 gating; __SHPRD_HOST_URL__ read (remoteHost.ts:9-28) with no injector repo-wide; window.confirm at ConfigMenu.tsx:587.

Rationale: Installability makes the no-host-UI-outside-iframe gap permanent on every phone; the fix is porting existing UI, not inventing new flows.

Downsides: Decides where host state lives (localStorage vs injected global) and how it reconciles with the desktop iframe path; the current confirm() UX is desktop-flavored and should be restyled mobile-first.
