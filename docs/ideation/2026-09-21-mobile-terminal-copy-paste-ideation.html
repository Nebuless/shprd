Compound Engineering · Ideation

Mobile terminal copy & paste for SHPRD

Date 2026-09-21 Topic mobile-terminal-copy-paste Focus Copy & paste in the terminal on mobile app / PWA (e.g. a copy mode) Mode: repo-grounded

Codebase Context

  • Stack: React web client (web/, xterm.js 6.1.0-beta with @xterm/addon-clipboard integrated), Rust server (server/), thin Android WebView wrapper (shprd-shell); PWA served over Tailscale (e.g. https://cax.tailc3b28.ts.net).
  • Copy today is desktop-only: the xterm onCopy handler (TerminalView.tsx:1635-1646, term.getSelection() → clipboard) never fires from touch gestures; OSC 52 inbound writes work live (TerminalView.tsx:963, writeText), outbound copy relies on programs emitting OSC 52.
  • Clipboard layering exists: terminalClipboard.ts owns a provider map with a 100k-char write cap, gesture-gated copyTextFromUserGesture(), and refuses programmatic reads; terminalPaste.ts runs the rich paste pipeline; TerminalComposer.tsx exposes a paste path.
  • Touch handlers (TerminalView.tsx:1908-2095) implement scroll + blur only — no long-press, no context menu, no selection UX on touch.
  • Configurable mobile affordances already shipped: mobileTerminalShortcuts.ts (configurable shortcut rows) and MobileTabSheet (toggle-sheet pattern) are the natural extension points.
  • Endpoint freeze precedent: presentation freezes repaints during mouse selection — a proven pattern to reuse for touch selection.
  • Prior art (external): Termux long-press context menu; Mobile SSH / Termius dedicated copy actions; xterm.js issue #3727 documents the touch copy/paste gap; e-reader / PDF text-layer selection as UX analogies.
  • Grounding scope: orchestrator-run shell probes + three direct web searches; learnings corpus empty (Files Scanned: 0); degraded-but-completed run.

Topic Axes

  1. Activation & entry — how a copy/paste interaction starts on a touchscreen
  2. Selection mechanics — how text is marked for copying without a mouse
  3. Destination & paste — where copied text goes and how it returns
  4. Mode safety & exit — how a selection/copy mode cannot corrupt or trap the terminal session
  5. Platform surface — PWA browser vs Android WebView capabilities and constraints

Ranked Ideas

  1. Copy Mode v1 (freeze + select + auto-copy)
  2. Long-press → terminal context menu
  3. One-tap Copy last output
  4. Copy pill on any selection
  5. Terminal block segmentation
  6. Server-side recent-output extraction API
  7. Paste safety chip (surface + preview)

1.Copy Mode v1 — freeze, tap-select, auto-copy on exit

Axes 1 · 2 · 4 · 5Confidence HighComplexity M

DescriptionA terminal-wide toggle (shortcut row or tab-sheet entry, following MobileTabSheet) that freezes presentation — the same mechanism the endpoint already uses during mouse selection — blocks the PTY from receiving taps, lets the user tap/drag to select text, and copies the selection to the clipboard when the mode exits, with the last-selection retained for retries. One toggle, one gesture, one tap on Copy: the whole loop the user named in the request.

AxisActivation & entry + selection mechanics (composite)

Basisdirect: endpoint freeze precedent in TerminalView.tsx (repaint freeze during selection, mouse path); direct: copyTextFromUserGesture() in terminalClipboard.ts is a ready, gesture-safe write primitive; direct: MobileTabSheet is an existing toggle-surface pattern. external: e-reader / PDF text-layer selection mode as UX analogy.

RationaleThe core gap is that no touch path currently selects terminal text — the desktop onCopy handler never fires from touch. A mode that reuses the proven freeze + a gesture-gated clipboard write closes the loop with the smallest set of new behaviors, and it degrades gracefully: a failed copy keeps the selection visible for retry.

DownsidesA mode toggle adds state to get wrong (entry/exit affordances, stale freeze if the app is backgrounded mid-mode); tap-blocking must be airtight or keystrokes leak into the PTY; power users may find mode-switching heavier than gestures.

Confidence85% — every mechanism has in-repo precedent; the integration order is the open question.

ComplexityMedium

2.Long-press → terminal context menu

Axis 1Confidence HighComplexity S

DescriptionA long-press on the terminal surface opens a small context menu — Copy, Paste, Select word — matching Android conventions, with the freeze + tap-block protections applied while the menu is up. This is the platform-convention entry point every Android user already knows from Termux.

AxisActivation & entry

Basisdirect: touch handlers (TerminalView.tsx:1908-2095) have scroll+blur only — zero long-press/contextmenu code, so this is net-new on a clean surface; external: Termux's long-press menu as the Android-terminal convention; direct: copyTextFromUserGesture() available for the menu's copy action.

RationaleThe verifier confirmed the gesture gap and the prior art. Long-press is the entry Android users already know — discoverability without teaching a new mode — and it composes with every selection mechanism in this list rather than competing with them.

DownsidesLong-press conflicts with scroll-hold expectations; menu items are only as good as the selection mechanics behind them (Copy without a selection story is a stub); WebView context-menu interception needs testing.

Confidence80% — entry point is solid; value depends on the selection mechanic it triggers.

ComplexityLow

3.One-tap Copy last output

Axis 2Confidence HighComplexity S

DescriptionA shortcut-row button (extending mobileTerminalShortcuts.ts) that copies the last command's output — from the last prompt to end of screen or scrollback — in a single tap. No selection, no mode: the 80% case ("grab that error / that ID") handled directly.

AxisSelection mechanics

Basisdirect: configurable shortcut-row infrastructure exists (mobileTerminalShortcuts.ts); direct: prompt-to-EOF extraction reuses the same freeze mechanism as selection; reasoned: terminal output is line-structured around prompts, so the dominant copy need has a programmatic boundary that needs no gesture.

RationaleSound verdict: the infrastructure and the write primitive are both confirmed in-repo, and the frequency argument is the strongest in the set — most mobile copy wants are "the last thing on screen," not arbitrary ranges. Cheapest path to a working copy feature for the exact scenario the user described.

DownsidesBoundary detection is heuristic (multi-page output, programs that redraw); copies more than the user wants sometimes; doesn't help mid-scrollback selection.

Confidence78% — extraction heuristics need tuning against real sessions.

ComplexityLow

4.Copy pill on any selection

Axis 1Confidence HighComplexity S

DescriptionWhen a selection exists (however it was made — mode, drag, native delegation), a floating Copy pill appears anchored near the selection, matching the desktop copy affordance on touch. The visible, discoverable commit step for any selection mechanism.

AxisActivation & entry

Basisdirect: the desktop selection → clipboard path exists (onCopy handler, TerminalView.tsx:1635-1646) and only lacks a touch trigger; direct: copyTextFromUserGesture() matches this exact interaction shape; external: mobile OS text-selection toolbar convention (the floating Copy pill is the standard pattern).

RationaleSound verdict: it is the smallest discoverable surface that makes any selection mechanic feel complete — and it is the idea to A/B against auto-copy-on-exit (idea 1) rather than a rival: explicit Copy beats implicit copy for long or partial selections the user may want to trim.

DownsidesRequires a selection mechanism to exist first (shipped alone it does nothing); pill positioning over a frozen canvas needs care; doubles the exit affordances with idea 1 unless they're merged.

Confidence72% — trivial once selection exists; easy to merge into idea 1.

ComplexityLow

5.Terminal block segmentation

Axis 2Confidence MediumComplexity M

DescriptionSegment the scrollback into prompt / command / output blocks and make each a tap target — notebook-cell granularity: tap a block to select the whole command or output unit. Finger-sized targets replace character-precision drags; block selection can extend by tapping neighbors.

AxisSelection mechanics

Basisdirect: frame-flow rendering confirmed in TerminalView.tsx; direct: an agent-history block component already exists in the codebase (the verifier confirmed the pattern's presence, while noting the terminal-side detection is a leap); external: notebook-cell interaction as the UX analogy.

RationaleWeak-basis verdict retained deliberately: segmentation is the strongest mechanic candidate because it converts an impossible gesture (character selection on a phone) into an easy one (tap a block). The prompt/output boundary detection is a real engineering leap — that risk is why confidence is Medium, not why the idea is cut.

DownsidesBoundary detection heuristics will mis-segment (continuations, TUI apps, multi-page output); per-block selection state adds UI complexity; weakest direct evidence of the survivors.

Confidence55% — high payoff, genuine detection risk.

ComplexityMedium

6.Server-side recent-output extraction API

Axis 5 · 2Confidence MediumComplexity M

DescriptionExpose recent terminal output through the server API — e.g. GET /api/terminals/:id/recent-output?lines=N — so a mobile surface can offer "copy last N lines / last command output" or "share output" without fighting touch-geometry selection at all. PWA and Android wrapper get the same endpoint.

AxisPlatform surface + selection mechanics

Basisdirect: the app already has server/endpoint API routes with a documented base-URL resolution helper (the absoluteApiUrl fix shipped in 0.9.2); direct: output already streams to the client as structured data the server sees; reasoned: server-side extraction sidesteps WebView clipboard permission walls entirely (the copy surface becomes a plain app view, not the xterm canvas).

RationaleSound verdict: it is the only survivor that treats the Android-WebView/PWA split as an asset — the platform axis the user's report actually lives on. It also unlocks share/export flows beyond clipboard that no touch gesture can reach.

DownsidesTouches the server (authz, size caps, redaction questions: secrets routinely appear in terminal output); duplicates client-side scrollback knowledge; API surface needs versioning discipline.

Confidence58% — architecture fits, but output-redaction policy must be designed first.

ComplexityMedium

7.Paste safety chip (surface + preview)

Axis 3Confidence MediumComplexity S

DescriptionConsolidate paste into one mobile surface: a persistent chip above the composer showing clipboard state (content present / read blocked), tapping it opens a multiline preview with an explicit "Insert" confirm — the paste-side complement to the copy ideas, completing the loop the user asked for.

AxisDestination & paste

Basisdirect: terminalPaste.ts rich paste runner and the composer paste path are confirmed; direct: clipboard read refusal is a confirmed behavior (the provider refuses programmatic reads), so a preview surface is the workaround the refusal demands; reasoned: a visible chip + confirm turns the riskiest terminal operation (paste) into a reviewed one.

RationaleWeak-basis verdict retained on meeting-test strength: the read-refusal fact makes preview/confirm the necessary shape on mobile, and the verifier called the consolidation a sound product move. Copy without a paste story would half-answer the user's request; this completes it.

DownsidesChip half inherits unresolved read-permission scoping (WebView secure-context walls may block reads app-wide, not just for the terminal provider); extra tap for a frequent action; vertical space above the composer.

Confidence60% — the preview half is solid; the chip half depends on clipboard read permissions.

ComplexityLow
