# Plan: Android-native feel for the SHPRD shell

## Goal Capsule

- **Objective:** A user who installs the SHPRD APK sees a first-class Android app at every step they never think about — launcher icon (including themed/monochrome icons), cold launch, and the system chrome around the terminal — instead of a generic browser wrapper.
- **Means:** An idempotent build-time native-overlay injection in `scripts/build-android.sh` that applies committed icon/theme/manifest resources into the dx-generated Android project (KTD1, KTD2).
- **Execution profile:** `execution: code`; this document is the gate artifact for human review. Implementation happens in a follow-on ce-work run after approval.
- **Authority hierarchy:** This plan governs the native-feel track; the mobile host-entry/connect-form logic belongs to the PWA-install-parity track and must not be modified here (R6).
- **Stop conditions:** Any change that would alter bootstrap URL flow, add per-build Node dependencies for asset generation, or require Kotlin/wry-fork work is out of scope — stop and record the divergence instead.

## Product Contract

### Summary
The Android APK currently ships a placeholder-grade launcher icon, a blank/white cold launch, and browser-default system bars around a dark `#1a1b26` terminal product. The Android project is generated by `dx build` and post-processed by `scripts/build-android.sh`, so every native surface must be injected idempotently at build time from committed sources.

### Problem Frame
The gap is visible in the first 60 seconds and daily thereafter: the icon reads as unfinished in the launcher and themed-icon mode; every cold launch flashes white before first paint; status/navigation bars and keyboard behave browser-default and fight the terminal UI; back gesture can end the session like closing a page. Comparable wrappers (Home Assistant Companion, Immich, Tailscale) treat all four as table stakes; Jellyfin shows the risk of not doing so.

### Requirements

- **R1 Idempotent native-overlay injection.** Every build deterministically applies a committed overlay — `res/` tree, theme XMLs, manifest additions — into `target/dx/shprd-shell/release/android/app` before `gradlew :app:packageRelease`. Re-runs produce identical results; layout-shape changes fail loudly.
- **R2 Single-source brand icon set.** One committed 1024×1024 source PNG yields the adaptive icon ladder (`mipmap-anydpi-v26` background/foreground/monochrome XML, per-density PNGs 108–432px with 66/108 safe zone, round + legacy fallbacks) and a 512×512 Play listing icon; brand palette `#1a1b26` / `#7aa2f7`.
- **R3 Dark-mode-aware brand splash.** `Theme.SplashScreen`-equivalent theme on API 31+: `windowSplashScreenBackground` `#1a1b26` + values-night light pair, brand icon layer, `postSplashScreenTheme`; graceful degradation pre-31.
- **R4 System-bar theming.** `<meta name="theme-color">` pairs in `web/index.html`; native `values`/`values-night` light/dark bar-icon appearance; correct under targetSdk 35 edge-to-edge; no double insets padding.
- **R5 Terminal correctness preserved.** `ime()` viewport resize, safe-area forwarding, `textZoom=100`, no algorithmic darkening, no mixed content — verified on device and encoded as release-gate checklist.
- **R6 No regression.** Bootstrap host flow, URL validation, and session safety untouched; existing tests stay green.

### Acceptance Examples
1. Install on Android 13+: launcher shows adaptive icon; long-press → themed icon renders the monochrome silhouette in the system tint.
2. Cold launch in system dark: splash background is `#1a1b26` from first frame; in system light: light pair; no white/blank frame at any stage.
3. Connect to a bridge: status + navigation bars match the page background in both themes; keyboard opens without hiding the terminal's bottom line; no double padding at notches.
4. Run `mise run shell:android` twice on a clean checkout: overlay-applied resources are byte-identical.

### Scope Boundaries
- In: icon ladder, splash, bar theming, injection mechanism, verification, deferred-affordance decision record.
- Out (deferred, see Decision Gate): back routing, file picker, DownloadManager, share passthrough, deep links, shortcuts, notifications, keep-screen-on, external file opener, persistent-shell rearchitecture, pull-to-refresh (rejected), TWA (rejected).

### Dependencies
- dx 0.7.10-generated project layout (`app/src/main/`), existing `scripts/build-android.sh`, `scripts/android-package.test.ts`, brand assets in `web/public/shprd-icon.png` (as source reference only).

### Outstanding Questions (reviewer)
- Q1: Committed generated assets (KTD2) — confirm acceptable.
- Q2: Hand-written values-v31 splash theme without `core-splashscreen` dependency (KTD3) — confirm acceptable.
- Q3: Persistent-shell fork — spike as follow-on track or park (Decision Gate below).
- Q4: Light-mode bar appearance follows system theme (recommended) vs force dark chrome — confirm.

## Planning Contract

### Key Technical Decisions

- **KTD1 — Injection point is `scripts/build-android.sh`, post-`dx build`, pre-`gradlew`.** dx regenerates `target/` every build, so the only durable customization surface is the existing post-processing script. A small `scripts/android-apply-overlay.sh` (called by `build-android.sh`) copies a committed `scripts/android-overlay/` tree into the generated project and applies XML patches to the generated `AndroidManifest.xml` (theme attach, `android:enableOnBackInvokedCallback="true"` for future-proofing, roundIcon). Failure to find expected generated paths exits non-zero (loud layout drift).
- **KTD2 — Assets are committed, not generated per build.** The icon ladder is generated ONCE from a 1024×1024 source PNG (via Image Asset Studio or `@capacitor/assets` run out-of-tree), reviewed, and committed under `scripts/android-overlay/app/src/main/res/…`. No new npm/gradle build dependency (constraint C1). Regeneration is a documented manual step, not a build step.
- **KTD3 — Splash theme is hand-written XML in `values-v31/`, no AndroidX splash library.** On API 31+ the native attributes (`android:windowSplashScreenBackground`, `android:windowSplashScreenAnimatedIcon`, `android:windowSplashScreenTheme`) work without the AndroidX library; the Activity theme is patched via the manifest overlay to a theme chain defined in `values-v31/themes.xml` plus a plain pair in `values/themes.xml`. Pre-31 devices keep today's behavior (accepted degradation; 2026 device base is overwhelmingly 31+). This avoids injecting an AndroidX gradle dependency into the generated build. [VERIFY]: confirm the dx-generated theme parent accepts the attribute set; if the generated theme parent rejects splash attrs, fall back to adding `core-splashscreen` (documented fallback inside U3).
- **KTD4 — Bar theming = web meta + native values-night pair.** The web side owns `<meta name="theme-color">` (dark `#1a1b26`, light from existing theme script's palette); the native side owns bar icon appearance via `values/` + `values-night/` `windowLightStatusBar`/`windowLightNavigationBar`. No `setStatusBarColor` calls (deprecated under edge-to-edge). Inset double-padding is avoided by NOT adding native inset handling; the page already uses `viewport-fit=cover` + `safe-area-inset` (Chromium M136+ forwards cutouts to WebView). [VERIFY] on device: wry inset forwarding on current WebView Chromium revs.
- **KTD5 — Monochrome layer is a separate flat-alpha asset** derived from the same source, checked for legibility at themed-icon sizes; not an automatic downconvert of the foreground (safe-zone + silhouette quality).

### Design / Sequencing

U1 (assets) → U2 (injector) → U3 (splash) and U4 (bars) in either order after U2 → U5 (verification + CI gate) last. U2 is the keystone; U3/U4 are its first consumers.

### Assumptions

- dx 0.7.10 keeps generating the standard gradle layout used by `build-android.sh` today.
- The generated `AndroidManifest.xml` is small enough for idempotent XML patching (attribute-level set, not rewrite).
- Reviewer approval of KTD2/KTD3 avoids the gradle-dependency path entirely.

### Deferred / Decision Gate (goes to reviewer)
Persistent local shell (own WebView + overlay state machine) would unlock back routing, file picker, downloads, share passthrough, shortcuts, notifications, keep-screen-on, file opener (all require WebView/Activity hooks wry does not expose — confirmed by research and by Home Assistant's Kotlin-only implementations). Cost is a multi-week native commitment with wry feasibility unproven. **This plan does not include it**; the reviewer is asked to rule: spike, park, or drop.

## Implementation Units

- **U1 — Brand source + committed icon ladder**
  - Goal: one source PNG and the full reviewed icon ladder committed.
  - Requirements: R2.
  - Files: `scripts/android-overlay/app/src/main/res/mipmap-*/…`, `scripts/android-overlay/brand/shprd-icon-source.png`.
  - Approach: derive 1024×1024 source from existing brand; generate ladder out-of-tree; commit; include `ic_launcher.xml`/`ic_launcher_round.xml` (adaptive, monochrome child) and Play 512 icon.
  - Test Scenarios: all density dirs populated; monochrome alpha-only; safe-zone eyeball recorded in PR.
  - Verification: file-presence assertions in U5's package test.
- **U2 — Idempotent overlay injector**
  - Goal: deterministic apply of committed overlay into generated project.
  - Requirements: R1, R6.
  - Files: `scripts/android-apply-overlay.sh` (new), `scripts/build-android.sh` (call it after asset copy, before gradlew), `scripts/android-package.test.ts` (extend).
  - Approach: `cp -R` overlay res tree; idempotent manifest patch (grep-before-apply; anchored insertions); `set -eu` fail-loud on missing generated paths; no-op re-run check.
  - Test Scenarios: run injector twice → byte-identical; corrupted generated layout → non-zero exit; CI test asserts overlay files post-build.
  - Verification: `bun run test scripts/android-package.test.ts`.
- **U3 — Splash theme values + manifest wiring**
  - Goal: brand splash on 31+, graceful pre-31.
  - Requirements: R3.
  - Files: `scripts/android-overlay/app/src/main/res/values/themes.xml`, `res/values-v31/themes.xml`, `res/drawable/splash_icon.xml` (+ PNG layers), manifest patch in injector (Activity theme).
  - Approach: KTD3; document core-splashscreen fallback trigger.
  - Test Scenarios: API 31+ emulator cold launch shows brand bg both themes; pre-31 boots with plain theme.
  - Verification: device/emulator checklist (U5).
- **U4 — theme-color meta + native bar appearance**
  - Goal: bars match page theme; edge-to-edge correct.
  - Requirements: R4, R5.
  - Files: `web/index.html` (meta tags + theme script sets both), `scripts/android-overlay/app/src/main/res/values/themes.xml` (+`values-night/`).
  - Approach: KTD4; light value pulled from existing light palette token.
  - Test Scenarios: both themes on device; notch device inset check; keyboard-over-terminal check.
  - Verification: device checklist; `bun run typecheck` for web change.
- **U5 — Verification matrix + CI gate**
  - Goal: release gate encoded.
  - Requirements: R1, R5, R6.
  - Files: `scripts/android-package.test.ts`, device-checklist doc (repo docs page or plan appendix).
  - Approach: extend package test for overlay integrity + idempotency; document device-matrix checklist (API 31+ phone, notch device, keyboard test, themed icon preview).
  - Test Scenarios: clean-clone build passes; second build byte-identical overlay.
  - Verification: `mise run ci`.

## Verification Contract

- `bun run precommit` (format/lint/typecheck/test) — must pass on every commit.
- `bun run test scripts/android-package.test.ts` — proves overlay injection (U2, U5).
- `mise run shell:android` — full Android build; run twice; overlay resources byte-identical (R1).
- Manual device matrix (recorded in PR): API 31+ device — splash both themes; themed icon tint; bars match page in dark/light; notch safe-area; keyboard terminal check; connect→terminal flow unchanged (R6).
- Behavioral skill evaluation: none required (no runtime logic changed).

## Definition of Done

- Global: all five units merged; precommit and `mise run ci` green; two consecutive `mise run shell:android` builds byte-identical for overlay resources; device checklist recorded; deferred-affordance decision recorded in the plan or its follow-on doc.
- Per-unit: each U's Verification line executed with output captured in the implementation run's verification evidence; abandoned-attempt code from exploration removed before done is declared.
- Cleanup: no generator scripts or temp assets left in-tree unless committed as owned sources; `.omp/` runtime dirs excluded from commits.
